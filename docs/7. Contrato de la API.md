# 7. Contrato de la API

## 7.1 Objetivo

La API pública constituye el contrato oficial entre la biblioteca y todas las aplicaciones consumidoras.

Su propósito es proporcionar un conjunto de operaciones estables, consistentes e independientes de cualquier tecnología utilizada para acceder a los servidores de correo.

Toda aplicación deberá interactuar exclusivamente mediante esta interfaz.

La implementación interna podrá evolucionar libremente siempre que este contrato permanezca compatible.

---

## 7.2 Principios del Contrato

La API deberá cumplir los siguientes principios fundamentales:

* Simplicidad.
* Consistencia.
* Estabilidad.
* Predictibilidad.
* Independencia del proveedor.
* Independencia del protocolo.
* Compatibilidad hacia atrás.

Las operaciones deberán representar acciones propias del dominio del correo electrónico y nunca detalles de implementación.

---

## 7.3 Identificación de Recursos

Todos los recursos administrados por la biblioteca deberán poseer identificadores propios.

Como mínimo existirán identificadores para:

* Cuenta.
* Carpeta.
* Mensaje.
* Adjunto.

Estos identificadores serán los únicos valores aceptados por la API para localizar recursos.

Los identificadores internos utilizados por cada proveedor permanecerán completamente ocultos.

---

## 7.4 Selección de la Cuenta

Toda operación que actúe sobre un servidor de correo deberá comenzar indicando el alias de la cuenta.

El alias constituye la identidad pública de una cuenta dentro del sistema.

Ninguna operación aceptará:

* Direcciones de correo.
* Servidores IMAP.
* Servidores SMTP.
* Credenciales.
* Tokens.
* Identificadores propios del proveedor.

La resolución del alias hacia la configuración correspondiente será responsabilidad exclusiva de la biblioteca.

---

## 7.5 Operaciones Funcionales

La API deberá organizarse alrededor de operaciones funcionales del dominio.

Como mínimo contemplará los siguientes grupos:

### Administración de cuentas

* Obtener cuentas disponibles.
* Consultar información de una cuenta.

### Administración de carpetas

* Listar carpetas.
* Crear carpetas.
* Renombrar carpetas.
* Eliminar carpetas.

### Administración de mensajes

* Listar mensajes.
* Leer mensajes.
* Buscar mensajes.
* Mover mensajes.
* Copiar mensajes.
* Eliminar mensajes.
* Marcar mensajes.
* Obtener información detallada.

### Envío

* Enviar mensajes.
* Responder mensajes.
* Reenviar mensajes.
* Guardar borradores.

### Adjuntos

* Obtener adjuntos.
* Descargar adjuntos.

La nomenclatura definitiva podrá definirse durante la implementación, pero siempre deberá respetar esta organización funcional.

---

## 7.6 Entidades Devueltas

Todas las operaciones devolverán entidades pertenecientes al dominio definido por la biblioteca.

Nunca se devolverán estructuras específicas del proveedor.

Como mínimo la API utilizará las siguientes entidades:

* Account
* Folder
* Message
* Attachment
* Recipient

Cada entidad deberá poseer una estructura consistente independientemente del origen de los datos.

---

## 7.7 Manejo de Conexiones

La administración del ciclo de vida de las conexiones forma parte exclusivamente de la implementación interna de la biblioteca.

La API pública nunca expondrá operaciones relacionadas con:

* Abrir conexiones.
* Cerrar conexiones.
* Crear sesiones.
* Mantener sesiones.
* Reutilizar conexiones.

Cada operación deberá ejecutarse de forma completamente transparente para el consumidor.

La estrategia utilizada podrá variar según el proveedor o las necesidades de optimización sin modificar el contrato público.

---

## 7.8 Manejo de Errores

La API deberá informar errores funcionales claramente diferenciados de los errores internos de implementación.

Los consumidores nunca recibirán información relacionada con:

* Protocolos utilizados.
* Credenciales.
* Configuración interna.
* Direcciones de servidores.
* Detalles propios del proveedor.

Los errores deberán describir únicamente el problema funcional ocurrido.

---

## 7.9 Compatibilidad

Toda nueva versión de la biblioteca deberá preservar el comportamiento definido por esta especificación.

La incorporación de nuevas capacidades deberá realizarse mediante ampliaciones del contrato y no mediante modificaciones incompatibles con las operaciones existentes.

La estabilidad del contrato tendrá prioridad sobre la organización interna del código.

---

## 7.10 Principio Rector del Contrato

La API representa el único punto de contacto entre las aplicaciones consumidoras y la biblioteca.

Los consumidores deberán conocer únicamente conceptos propios del dominio del correo electrónico.

Toda información técnica relacionada con protocolos, autenticación, conexiones, proveedores, formatos internos o mecanismos de comunicación permanecerá encapsulada dentro de la implementación.

Este principio garantiza una interfaz limpia, estable y preparada para evolucionar sin afectar a las aplicaciones que dependan de ella.
