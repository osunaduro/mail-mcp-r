# 3. Arquitectura General

## 3.1 Visión General

El sistema estará compuesto por dos componentes principales claramente diferenciados:

* La biblioteca de gestión de correo electrónico, que constituye el núcleo funcional del proyecto.
* El servidor MCP, cuya única finalidad será exponer las capacidades de la biblioteca como herramientas consumibles mediante el protocolo MCP.

Ambos componentes deberán mantenerse desacoplados, permitiendo que cada uno pueda evolucionar o incluso ser reemplazado sin afectar al otro.

La biblioteca deberá poder utilizarse de forma independiente, sin requerir la existencia del servidor MCP.

---

## 3.2 Componentes del Sistema

La arquitectura estará organizada en las siguientes capas:

### Biblioteca de Correo (Core)

Es el componente principal del proyecto.

Será responsable de:

* Administrar las cuentas configuradas.
* Establecer conexiones con los servidores de correo.
* Gestionar la autenticación.
* Ejecutar todas las operaciones relacionadas con mensajes, carpetas y adjuntos.
* Traducir las operaciones funcionales hacia el protocolo correspondiente.
* Representar toda la información mediante entidades propias del dominio.

Toda la lógica de negocio residirá exclusivamente en este componente.

---

### Servidor MCP

Este componente actuará como una capa de integración.

Su única responsabilidad será publicar como herramientas MCP las funcionalidades ofrecidas por la biblioteca.

El servidor MCP no implementará reglas de negocio, algoritmos propios ni lógica relacionada con el funcionamiento del correo electrónico.

Cada herramienta expuesta deberá limitarse a:

* Validar los parámetros recibidos.
* Invocar la operación correspondiente de la biblioteca.
* Devolver el resultado obtenido.

Cualquier comportamiento adicional deberá implementarse en la biblioteca y nunca dentro del servidor MCP.

---

### Aplicaciones Consumidoras

Las aplicaciones consumidoras podrán utilizar el sistema de dos maneras:

* Integrándose directamente con la biblioteca.
* Consumiendo las herramientas expuestas por el servidor MCP.

En ambos casos deberán obtener exactamente el mismo comportamiento funcional.

---

## 3.3 Flujo de Ejecución

Todas las operaciones seguirán el mismo flujo conceptual.

1. El consumidor solicita una operación.
2. Si utiliza MCP, el servidor recibe la solicitud.
3. El servidor MCP delega la operación en la biblioteca.
4. La biblioteca identifica la cuenta correspondiente.
5. La biblioteca determina el mecanismo de comunicación necesario.
6. Se ejecuta la operación contra el servidor de correo.
7. La respuesta se transforma a las entidades del dominio.
8. El resultado vuelve al consumidor.

Este flujo deberá mantenerse para todas las funcionalidades del sistema.

---

## 3.4 Dependencias Permitidas

Las dependencias entre componentes deberán respetar la siguiente dirección:

Aplicación → MCP → Biblioteca → Servidor de Correo

o bien

Aplicación → Biblioteca → Servidor de Correo

Nunca deberán existir dependencias en sentido contrario.

La biblioteca no deberá depender del servidor MCP.

El servidor de correo nunca deberá comunicarse directamente con el servidor MCP sin pasar por la biblioteca.

---

## 3.5 Dependencias Prohibidas

Con el fin de preservar la arquitectura, quedan expresamente prohibidas las siguientes situaciones:

* Que el servidor MCP implemente lógica de negocio.
* Que una aplicación consumidora invoque directamente un protocolo de correo.
* Que la biblioteca conozca detalles del protocolo MCP.
* Que los consumidores manipulen estructuras internas propias de un proveedor de correo.
* Que existan dependencias circulares entre componentes.

Estas restricciones forman parte del diseño arquitectónico y deberán respetarse durante toda la vida del proyecto.

---

## 3.6 Comunicación entre Componentes

La comunicación entre los distintos componentes deberá realizarse exclusivamente mediante interfaces públicas claramente definidas.

Los componentes no deberán acceder a estructuras internas pertenecientes a otros módulos.

Toda interacción deberá producirse mediante contratos estables que permitan modificar la implementación interna sin afectar al resto del sistema.

---

## 3.7 Gestión de la Configuración

La configuración del sistema será cargada exclusivamente por la biblioteca durante su inicialización.

El servidor MCP nunca accederá directamente al archivo de configuración.

Toda la información relacionada con cuentas disponibles, credenciales, servidores y parámetros de conexión será administrada únicamente por la biblioteca.

Esto garantiza la existencia de una única fuente de configuración para todo el sistema.

---

## 3.8 Escalabilidad Arquitectónica

La arquitectura deberá permitir incorporar nuevos componentes sin modificar los ya existentes.

En el futuro podrán desarrollarse nuevas capas de integración, interfaces gráficas, servicios web, procesos automatizados u otros servidores de exposición que reutilicen la misma biblioteca.

Del mismo modo, podrán incorporarse nuevos mecanismos de acceso al correo sin alterar la API pública utilizada por las aplicaciones consumidoras.

La arquitectura deberá favorecer la evolución del proyecto mediante extensión y no mediante modificaciones que rompan el diseño original.

---

## 3.9 Principio Arquitectónico Principal

La biblioteca constituye el núcleo funcional del sistema.

Todo componente externo deberá considerar a la biblioteca como la única autoridad para realizar operaciones relacionadas con correo electrónico.

El servidor MCP, así como cualquier otra integración futura, será únicamente un consumidor de la biblioteca y nunca una implementación alternativa de su lógica.

Este principio garantiza una única implementación del dominio del negocio, evita duplicación de código y asegura un comportamiento uniforme en todos los puntos de acceso al sistema.
