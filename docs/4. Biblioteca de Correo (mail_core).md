# 4. Biblioteca de Correo (mail_core)

## 4.1 Objetivo

La biblioteca de correo constituye el núcleo funcional del proyecto.

Su propósito es ofrecer una interfaz única, consistente y desacoplada para administrar cuentas de correo electrónico previamente configuradas, ocultando completamente la complejidad técnica necesaria para comunicarse con los distintos servidores de correo.

Toda la lógica de negocio relacionada con el correo electrónico deberá implementarse exclusivamente dentro de este componente.

---

## 4.2 Responsabilidades

La biblioteca será responsable de:

* Cargar y validar la configuración de las cuentas disponibles.
* Administrar la autenticación con los distintos servidores de correo.
* Establecer y mantener las conexiones necesarias.
* Ejecutar todas las operaciones sobre mensajes, carpetas y adjuntos.
* Administrar los distintos mecanismos de comunicación soportados.
* Representar toda la información mediante entidades propias del dominio.
* Gestionar errores y excepciones relacionadas con el acceso al correo.
* Garantizar un comportamiento uniforme independientemente del proveedor utilizado.

Ninguna de estas responsabilidades deberá implementarse fuera de la biblioteca.

---

## 4.3 Responsabilidades Excluidas

La biblioteca no deberá asumir responsabilidades ajenas a la gestión del correo electrónico.

En particular, no deberá:

* Implementar el protocolo MCP.
* Contener lógica de interfaz de usuario.
* Administrar autenticación de usuarios finales de una aplicación.
* Gestionar permisos externos al sistema.
* Implementar reglas específicas de una aplicación consumidora.
* Depender de componentes externos distintos a los necesarios para acceder al correo.

---

## 4.4 Modelo del Dominio

La biblioteca representará el correo electrónico mediante un conjunto de entidades propias.

Estas entidades constituirán el lenguaje común utilizado por todas las aplicaciones consumidoras.

Como mínimo deberán existir las siguientes entidades conceptuales:

* Cuenta (Account)
* Carpeta (Folder)
* Mensaje (Message)
* Adjunto (Attachment)
* Destinatario (Recipient)

En futuras versiones podrán incorporarse nuevas entidades sin modificar el comportamiento de las existentes.

---

## 4.5 Operaciones Públicas

La biblioteca deberá ofrecer una API pública orientada a operaciones funcionales del dominio y no a operaciones específicas de un protocolo.

Las operaciones disponibles deberán permitir, entre otras capacidades:

### Gestión de cuentas

* Obtener las cuentas disponibles.
* Consultar información básica de una cuenta.

### Gestión de carpetas

* Listar carpetas.
* Crear carpetas.
* Renombrar carpetas.
* Eliminar carpetas.

### Gestión de mensajes

* Listar mensajes.
* Leer un mensaje.
* Buscar mensajes.
* Mover mensajes.
* Copiar mensajes.
* Eliminar mensajes.
* Marcar mensajes como leídos.
* Marcar mensajes como no leídos.
* Marcar mensajes como destacados.

### Envío

* Enviar mensajes.
* Responder mensajes.
* Reenviar mensajes.
* Guardar borradores.

### Adjuntos

* Obtener la lista de adjuntos.
* Descargar adjuntos.

La implementación interna de cada operación dependerá del proveedor correspondiente, pero su comportamiento deberá ser uniforme para el consumidor.

---

## 4.6 Abstracción del Proveedor

La biblioteca será la única responsable de determinar cómo ejecutar cada operación según el tipo de cuenta configurada.

Las aplicaciones consumidoras nunca deberán seleccionar manualmente un mecanismo de comunicación.

Únicamente indicarán sobre qué cuenta desean trabajar.

La biblioteca resolverá automáticamente la tecnología apropiada para dicha cuenta.

Este comportamiento deberá ser completamente transparente para el consumidor.

---

## 4.7 Gestión de Identificadores

Cada mensaje, carpeta y entidad administrada por la biblioteca deberá poseer un identificador estable dentro del contexto de la propia biblioteca.

Los identificadores internos utilizados por cada proveedor permanecerán encapsulados y nunca formarán parte del contrato público.

Esto permitirá mantener una API uniforme independientemente de la tecnología utilizada por cada servidor de correo.

---

## 4.8 Manejo de Errores

La biblioteca será responsable de transformar los errores técnicos generados por los distintos proveedores en errores consistentes y comprensibles para las aplicaciones consumidoras.

Las excepciones deberán describir el problema funcional ocurrido sin exponer detalles internos del protocolo o del proveedor.

Siempre que resulte posible, los mensajes de error deberán facilitar el diagnóstico sin revelar información sensible como credenciales, direcciones de servidores o datos internos de configuración.

---

## 4.9 Extensibilidad

La biblioteca deberá estar preparada para incorporar nuevos mecanismos de acceso al correo sin modificar la API pública.

La incorporación de un nuevo proveedor no deberá afectar el funcionamiento de los ya existentes.

Toda nueva implementación deberá integrarse respetando las mismas entidades del dominio, los mismos contratos y las mismas reglas de comportamiento definidas por esta especificación.

---

## 4.10 Principio Rector de la Biblioteca

La biblioteca constituye la única implementación autorizada de la lógica de negocio relacionada con el correo electrónico.

Toda aplicación, servicio o servidor que necesite interactuar con cuentas de correo deberá hacerlo exclusivamente mediante su interfaz pública.

Ningún componente externo podrá acceder directamente a los protocolos de comunicación, a las estructuras internas de los proveedores ni a los mecanismos de autenticación implementados por la biblioteca.

Este principio garantiza una única fuente de comportamiento, evita duplicación de lógica y asegura un funcionamiento uniforme para todos los consumidores presentes y futuros del sistema.
