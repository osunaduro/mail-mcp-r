# 2. Principios de Arquitectura

## 2.1 Objetivo

La arquitectura del proyecto deberá garantizar un diseño modular, desacoplado y extensible, permitiendo la incorporación de nuevas funcionalidades y tecnologías sin afectar la interfaz pública de la biblioteca ni a las aplicaciones que la consuman.

Todas las decisiones de implementación deberán respetar los principios definidos en esta sección.

---

## 2.2 Separación de Responsabilidades

El sistema estará dividido en componentes con responsabilidades claramente definidas.

Cada componente deberá resolver únicamente el problema para el cual fue diseñado.

En consecuencia:

* La biblioteca será responsable de toda la lógica relacionada con la gestión del correo electrónico.
* El servidor MCP será responsable únicamente de exponer las capacidades de la biblioteca como herramientas MCP.
* Las aplicaciones consumidoras serán responsables exclusivamente de utilizar dichas herramientas o la API pública de la biblioteca.

Ningún componente deberá asumir responsabilidades pertenecientes a otro.

---

## 2.3 Independencia del Protocolo

La biblioteca deberá abstraer completamente el protocolo utilizado para comunicarse con cada servidor de correo.

Los consumidores de la biblioteca nunca deberán conocer si una cuenta utiliza IMAP, Exchange, Microsoft Graph o cualquier otro mecanismo de comunicación.

Toda interacción deberá realizarse mediante operaciones funcionales de alto nivel relacionadas con el dominio del correo electrónico y no con el protocolo utilizado para implementarlas.

Este principio permitirá reemplazar o incorporar nuevos protocolos sin modificar la interfaz pública de la biblioteca.

---

## 2.4 Independencia del Proveedor

La biblioteca no estará diseñada para un proveedor específico de correo electrónico.

Su arquitectura deberá permitir administrar cuentas pertenecientes a diferentes servicios utilizando exactamente la misma interfaz pública.

Las diferencias técnicas existentes entre los distintos proveedores deberán permanecer completamente encapsuladas dentro de la implementación interna de la biblioteca.

Para el consumidor, todas las cuentas deberán comportarse de manera uniforme.

---

## 2.5 API Estable

La interfaz pública de la biblioteca constituye un contrato con todas las aplicaciones consumidoras.

Las modificaciones internas de implementación nunca deberán alterar dicho contrato.

Las nuevas funcionalidades deberán incorporarse manteniendo la compatibilidad con versiones anteriores siempre que resulte técnicamente posible.

La estabilidad de la API tendrá prioridad sobre las decisiones de implementación interna.

---

## 2.6 Bajo Acoplamiento

Los distintos componentes del sistema deberán mantener el menor nivel posible de dependencia entre sí.

La biblioteca no dependerá del servidor MCP.

El servidor MCP dependerá de la biblioteca únicamente mediante su interfaz pública.

Las aplicaciones consumidoras dependerán exclusivamente de la API documentada de la biblioteca o de las herramientas expuestas por el servidor MCP.

Esta organización permitirá reutilizar cada componente de forma independiente.

---

## 2.7 Alta Cohesión

Cada componente deberá agrupar únicamente funcionalidades relacionadas con una misma responsabilidad.

La biblioteca contendrá exclusivamente lógica de gestión de correo electrónico.

El servidor MCP contendrá exclusivamente lógica de exposición de herramientas.

La configuración contendrá exclusivamente información necesaria para la definición de las cuentas administradas.

La mezcla de responsabilidades entre componentes queda expresamente desaconsejada.

---

## 2.8 Configuración Centralizada

Todas las cuentas administradas por el sistema deberán definirse en un único archivo de configuración mantenido por el administrador.

La incorporación, modificación o eliminación de cuentas será una tarea administrativa y nunca una operación disponible para los consumidores de la biblioteca o del servidor MCP.

Las credenciales, parámetros de conexión y cualquier información sensible permanecerán exclusivamente dentro de dicho archivo de configuración.

---

## 2.9 Abstracción del Dominio

La biblioteca representará el correo electrónico mediante entidades propias del dominio.

Los consumidores interactuarán con conceptos como cuentas, carpetas, mensajes y adjuntos.

Nunca deberán manipular estructuras de datos específicas de un protocolo o proveedor.

Este principio garantiza que el dominio del problema permanezca estable aunque cambien las tecnologías utilizadas para resolverlo.

---

## 2.10 Extensibilidad

La arquitectura deberá facilitar la incorporación de nuevas capacidades sin requerir modificaciones sobre los componentes existentes.

La incorporación de un nuevo proveedor de correo, un nuevo protocolo o una nueva funcionalidad deberá realizarse mediante la extensión de la arquitectura y no mediante la modificación del comportamiento ya implementado.

Este principio busca reducir el impacto de futuras evoluciones del proyecto y preservar la estabilidad de las aplicaciones consumidoras.

---

## 2.11 Principio Fundamental

Toda complejidad técnica deberá permanecer encapsulada dentro de la biblioteca.

Ningún consumidor, incluido el servidor MCP, deberá conocer detalles de implementación relacionados con protocolos, autenticación, formatos internos, identificadores propios de los proveedores o mecanismos de comunicación.

La biblioteca constituye la única fuente de conocimiento sobre cómo interactuar con los distintos sistemas de correo electrónico.

Toda aplicación que utilice el proyecto deberá trabajar únicamente con los conceptos funcionales definidos por esta arquitectura.
